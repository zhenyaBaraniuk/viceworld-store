# Quickstart: Validating Product Labels

Manual/automated validation scenarios proving the feature works end-to-end, mapped to the
Acceptance Scenarios in `spec.md`. Full field/table shapes are in `data-model.md`; the
frontend↔backend payload shape is in `contracts/product-page-props.md`. Implementation steps
live in `tasks.md` (generated by `/speckit-tasks`), not here.

## Prerequisites

- Laradock containers running (Constitution Principle II — never run `php artisan`/`composer`
  bare on host).
- Latest migrations applied inside the container: `php artisan migrate`.
- Logged into `/admin` as a user with the `admin` role (has every permission via
  `RolesAndPermissionsSeeder`).

## Scenario 1 — Admin manages the label catalog (User Story 1, P1)

1. Go to `/admin` → Catalog → Labels → Create.
2. Enter a name for each locale (e.g. `uk`: "Основна колекція", `en`: "Core Collection"). Save.
3. **Expect**: label appears in the Labels list; reopening it for edit shows both locale values.
4. Edit the `uk` name, save, reopen — **expect** the change persisted.
5. Delete the label (not yet assigned to any product) — **expect** it disappears from the list
   and is no longer offered in the product's label picker.

## Scenario 2 — Admin assigns labels to a product, in order (User Story 2, P2)

1. Create two labels: "Core Collection", "Limited Edition" (both locales).
2. Open any product in `/admin` → Products → edit.
3. In the Labels field, select "Limited Edition" first, then "Core Collection". Save.
4. Reopen the product — **expect** both labels shown as selected, in the order selected
   (Limited Edition, then Core Collection) — verifies FR-010 / the Clarifications decision.
5. Remove "Limited Edition", save, reopen — **expect** only "Core Collection" remains.
6. In the label picker, type a partial name — **expect** matching labels to appear regardless of
   the admin UI's current locale.

## Scenario 3 — Customer sees labels on the product page (User Story 3, P3)

1. Visit the public product page (`/{locale}/products/{slug}`) for the product from Scenario 2.
2. **Expect**: the labels render, translated into `{locale}`, in assignment order, in the
   `product-info__meta` line (replacing the old static "Core Collection • Limited Edition" text)
   — see `contracts/product-page-props.md` for the exact payload shape.
3. Visit the product page of a product with **no** labels assigned.
4. **Expect**: no label line renders at all — no empty `<p>`, no leftover static text (FR-006).
5. Switch `{locale}` in the URL (`/uk/...` ↔ `/en/...`) — **expect** the label text changes
   language without changing order.

## Edge cases to spot-check

- Delete a label that **is** currently assigned to a product → product page for that product no
  longer shows it; the product itself is otherwise unaffected (FR-008).
- Create two labels with the identical name in the same locale → both save successfully and can
  be assigned independently (spec Edge Cases: no uniqueness constraint).

## Automated checks (must exist and pass before this feature is considered done)

- `tests/Feature/Catalog/*` (new, per `research.md` §6) covering: label CRUD via the admin
  resource (policy-gated), label↔product assignment persistence and order, `ProductData`
  serializing `labels` in the right shape/order, and the product page hiding the label line when
  `labels` is empty.
- Run inside Laradock: `composer check` (pint → rector dry-run → phpstan → full test suite) for
  any PHP change; `npm run fix` (typecheck → lint:fix → format) for the `Product.tsx` /
  `product.ts` changes.
